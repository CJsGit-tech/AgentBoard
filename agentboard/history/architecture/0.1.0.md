# Technical Architecture — AgentBoard

> Owner: Solution Architect | Version: 0.1.0 | Status: draft | Last Updated: 2026-11-17
> Based on: Product Vision v0.1.2; User Stories v0.1.1 (both drafts)

## 1. Scope & Architecture Summary

A local browser application for one builder coordinating projects, agent role definitions, tasks, documents, and progress. Docker Compose manages one application service. A compiled React frontend and a FastAPI HTTP API share one origin; SQLite stores the application data in a named Docker volume.

Confirmed deployment direction: local web app with Docker Compose infrastructure. The stack below is a proposed architectural decision, not a previously approved requirement. Current stories define manual coordination, not agent launching, shell execution, or live agent telemetry. Those capabilities require a separate integration and security design if requested.

## 3. High-Level System Architecture

Diagram: [system-architecture.svg](./system-architecture.svg).

- Browser: project navigation, role editor, task list/detail, document editor, progress view, task activity. Keeps unsaved edits until success or an explicit discard; does not treat errors as empty data.
- Compose service `app`: serves compiled frontend assets, `/api/v1` routes, and health endpoints. One Uvicorn worker initially.
- API services: validate input, enforce project membership and invariants, coordinate transactions, and expose consistent error responses.
- SQLite repository: durable domain records, optimistic concurrency, and transactional activity records. Database path `/data/agentboard.sqlite3`.
- Named volume `agentboard_data`: mounted at `/data`; survives application container replacement. Browser storage is not the canonical database.

Request flow: browser → loopback HTTP endpoint → API validation/service → SQLite transaction → response → frontend refresh. Static assets share the HTTP origin; client routes use an explicit SPA fallback after API routes, with missing API paths returning JSON 404 rather than HTML.

External integrations: N/A for current stories. Agent roles are records, not processes. This app does not automatically consume the AgentBuild planning folder; importing these planning artifacts would be a separate feature.

## 4. Technology & SDK Decisions

| Layer | Proposed selection | Rationale | Alternative / tradeoff | Confidence |
| --- | --- | --- | --- | --- |
| Frontend | React, TypeScript, Vite | Component-based forms and project views; static build served by the application | Server-rendered templates reduce JS but complicate rich editing state | Design choice; exact versions unverified |
| API | FastAPI, Pydantic, Uvicorn | Typed validation and inspectable OpenAPI contracts | TypeScript backend shares language but is not required by existing constraints | Container/static-serving capabilities documented; combined build untested |
| Persistence | SQLite via Python sqlite3 | Simple local relational storage without another service | PostgreSQL better fits multiple writers/services; extra operations for present scope | Appropriate local use documented; workload unbenchmarked |
| Schema evolution | Ordered SQL migrations with schema version table | Explicit upgrades without an ORM requirement | ORM migration framework adds tooling if model complexity grows | Proposed |
| Delivery | Multi-stage Docker build; Docker Compose | Repeatable local startup and isolated dependencies | Separate web/API/database services add independently deployable parts but more setup | Docker persistence model documented; images not built |

Vite provides a production build; FastAPI supports static-file serving and container deployment. The single-container combination is an architectural inference, not a tested compatibility claim. See official references below.

## 5. Data & Storage Design

All IDs are server-generated UUIDs. Timestamps are UTC; UI formats them for the builder. Mutable records carry integer `revision`, `created_at`, and `updated_at`.

| Entity | Main fields / rules | Stories |
| --- | --- | --- |
| Project | id, name, purpose; nonblank trimmed name, duplicate names allowed | US-001–002 |
| AgentRole | id, project_id, name, responsibilities; both text fields required | US-003 |
| Task | id, project_id, title, description, priority, status, owner_kind, role_id, blocker_reason, revision | US-004–006 |
| Document | id, project_id, title, content, revision; nonblank title/content | US-007 |
| TaskDocument | project_id, task_id, document_id, relationship (`context` or `output`); unique tuple | US-008 |
| TaskActivity | id, task_id, project_id, field, old_value, new_value, changed_at; append only | US-010 |

Task defaults: Normal priority, Planned status, Unassigned owner. These are proposed conventions. Owner kinds: `unassigned`, `builder`, `role`; role_id is set only for role ownership. Status values: Planned, In Progress, Blocked, Done. Blocked requires nonblank explanation; leaving Blocked clears its current reason. Priority values: High, Normal, Low.

Enable foreign keys on every connection. Composite project/id constraints prevent cross-project role assignments and document associations. Task edits and corresponding activity entries commit together; failed transactions create neither state changes nor history. Use revision-checked writes to prevent one tab silently overwriting another.

Configure WAL mode and bounded busy timeout; keep transactions short. A busy database returns a recoverable error rather than success. One service instance accesses the database on a local Docker volume; no network filesystem or horizontally scaled writers. Progress uses grouped queries over current tasks, not a separately updated counter. Add indexes for project/status, project/priority, document project, and task activity order.

Retention: records persist until explicitly changed; deletion and automatic purging are outside current stories. Document revision browsing is deferred; revision numbers detect conflicts but do not imply retained document versions. Backups preserve the entire database, including task activity.

## 6. API / Interface Contracts

All domain routes are under `/api/v1`. IDs are opaque and project-scoped. JSON writes require `application/json`. Browser accesses relative paths on the same origin.

| Route | Behavior |
| --- | --- |
| GET/POST `/projects` | List/create projects; stable ordering and bounded pagination |
| GET/PATCH `/projects/{projectId}` | Read/update name and purpose |
| GET/POST `/projects/{projectId}/roles` | List/create role definitions |
| PATCH `/projects/{projectId}/roles/{roleId}` | Update role name/responsibilities |
| GET/POST `/projects/{projectId}/tasks` | Filter by status/priority/owner, list/create tasks |
| GET/PATCH `/projects/{projectId}/tasks/{taskId}` | Read/update task; assignment and status included |
| GET/POST `/projects/{projectId}/documents` | List metadata/create document |
| GET/PATCH `/projects/{projectId}/documents/{documentId}` | Read/update content |
| GET/POST `/projects/{projectId}/tasks/{taskId}/documents` | List links; create relationship idempotently |
| DELETE `/projects/{projectId}/tasks/{taskId}/documents/{documentId}/{relationship}` | Remove link only |
| GET `/projects/{projectId}/progress` | Counts per status and total; no tasks represented explicitly |
| GET `/projects/{projectId}/tasks/{taskId}/activity` | Paginated ownership/status history |

Create returns 201 and the saved record; successful reads/updates return 200, link removal returns 204. PATCH requires the current revision; mismatch returns 409 with current revision and instructs the client to reload or reconcile. Duplicate identical document links return the existing association. Missing or cross-project resources return 404. Invalid input returns 422 with field details; oversize documents return 413; temporary storage failures return 503. Errors use `{error: {code, message, fields}, request_id}`; frontend never clears input on failure.

Pagination: default 50, maximum 100, stable order plus ID tie-break; task priority order is High → Normal → Low. GET `/health/live` checks process responsiveness; `/health/ready` checks schema readiness and a database read. Route names are proposed contracts for the new app, not claims of an existing AgentBoard API.

## 7. Frontend Folder Structure

Proposed paths under the future application repository:

```text
frontend/
  src/
    app/                 # navigation and project context
    features/
      projects/
      roles/
      tasks/
      documents/
      progress/
    components/          # shared controls, empty/error states
    api/                 # typed HTTP client, error handling
    tests/               # forms and user workflows
  public/
  package.json
```

Keep server data distinct from editable draft state. After a successful mutation, refresh affected lists and progress. On failed requests, show retry and retain input. In-memory project selection must not override project IDs used in requests.

## 9. Security & Nonfunctional Requirements

- Bind the host port as `127.0.0.1:8080:8000`; the process listens inside its container on port 8000. Access from other computers is not part of this design.
- Assumption: trusted local OS account, no app login for the first release. Local malware/other local users are outside this boundary; exposing the service to LAN or internet requires authentication and a revised deployment design.
- Validate Host and Origin against the configured loopback origin. Require a session-bound CSRF token on mutations; disable permissive CORS. Use HttpOnly, SameSite cookies for the local session. Do not trust loopback binding alone as request authorization.
- Run as a non-root container user with a writable data volume, no Docker socket or arbitrary host directory mounts. Role/document text is inert content; never execute it. Render Markdown with raw HTML disabled and safe URL handling; add a restrictive content security policy.
- No provider secrets or AI calls are needed for the scoped stories. Keep document bodies and sensitive fields out of logs; log request IDs, outcome codes, and elapsed time.
- Proposed performance target: p95 reads below 300 ms and saves below 500 ms at the stated data envelope on an agreed reference machine, excluding first launch. Benchmark before treating these as achieved.
- Accessibility target: keyboard-operable core flows, labeled controls, visible focus, and non-color-only status. Verify during Design Profile and browser testing.
- Reliability tests: restart preserves data; failed transactions leave no partial task/history; cross-project constraints reject invalid links; stale writes return conflict; failed saves preserve drafts; overview failure differs from zero tasks. Browser tests cover US-001 through US-010.

## 10. Deployment & Operations

Proposed Compose service `app` builds the frontend in a Node stage and copies assets into a Python runtime. It mounts named volume `agentboard_data` at `/data`, publishes only the loopback port, defines a readiness healthcheck, and uses a restart policy appropriate for local startup. No database container, queue, cache, or service dependency ordering is needed for this design.

Before opening the listener, run ordered migrations in a single process and refuse readiness if migrations fail. Startup must fail with an actionable error if the data directory is unwritable. Pin dependencies and images during implementation; verify clean build, migration, startup, and restart. No container has been built or started in this planning command.

Normal lifecycle will use `docker compose up -d --build` and `docker compose down` once actual configuration exists. Named-volume persistence is documented by Docker; deleting the volume removes the application data. Back up before upgrades: stop the app, copy the complete data volume into a dated archive outside that volume, then restart. Restore into a separate volume and verify schema, record counts, and sample documents before replacing active data. Restore and rollback instructions must be exercised during implementation. An older image may not read a newer schema; rollback uses the matching pre-upgrade backup.

Optional development override: frontend development server with API proxy and backend reload; runtime release continues to serve compiled assets. Network access for build dependencies is separate from normal offline use.

## 11. Architectural Decisions

| ID | Decision | Rationale | Consequence | Related stories |
| --- | --- | --- | --- | --- |
| ADR-001 | Local web delivery through Compose | Confirmed product-owner constraint | Docker required locally | US-001–010 |
| ADR-002 | One app container with same-origin frontend/API | Proposed simple operational boundary | Frontend/backend released together | US-001–009 |
| ADR-003 | SQLite in a named volume | Proposed local relational storage | Single-instance writer model; backup required | US-001–010 |
| ADR-004 | Manual task state and inert agent role records | Matches current story acceptance criteria | Execution integrations need later scope | US-003, US-005–006 |
| ADR-005 | Revision checks and transactional task activity | Avoid lost changes and false history | Clients handle conflicts explicitly | US-001, US-003–007, US-010 |
| ADR-006 | Project-scoped constraints and queries | Prevent mixing project contexts | Validate relations on every write | US-002, US-005, US-008–009 |

Except ADR-001, decisions are draft proposals requiring review, not human approvals.
