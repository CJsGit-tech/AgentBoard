## Detailed User Stories

### US-001 — Create a product project

**Story:** As a solo builder, I want to create a project with its purpose so that its work and documents share a clear context.

**Priority:** Must

**Links:** Product project management

**Dependencies:** None

**Acceptance Criteria:**

1. **Given** a project name and optional purpose, **when** I save a new project, **then** it appears in my project list and opens with the saved details.
2. **Given** a blank or whitespace-only name, **when** I save, **then** creation is prevented with a clear explanation and my other input is retained.
3. **Given** an existing project, **when** I change its name or purpose and save, **then** its existing tasks, roles, and documents remain associated with it.
4. **Given** a save failure, **when** creation or editing fails, **then** the app does not report success and preserves my input for retry.

**Open questions:** None blocking. Assumption: a name is required and purpose is optional.

### US-002 — Find and switch projects

**Story:** As a solo builder, I want to find and reopen my projects so that I can resume the right work without mixing contexts.

**Priority:** Must

**Links:** Product project management

**Dependencies:** US-001

**Acceptance Criteria:**

1. **Given** multiple projects, **when** I open the project list and select one, **then** its identity is visible and its tasks, roles, and documents are shown.
2. **Given** an active project, **when** I switch to another, **then** the displayed records belong to the selected project rather than the previous one.
3. **Given** no projects, **when** I open the list, **then** an empty state offers project creation.
4. **Given** projects with the same name, **when** I inspect the list, **then** another visible identifying detail lets me distinguish them.

**Open questions:** None blocking. Assumption: duplicate names are allowed with distinct project identities.

### US-003 — Define project agent roles

**Story:** As a solo builder, I want to define agent roles and responsibilities so that I can make clear assignments.

**Priority:** Must

**Links:** Agent role management

**Dependencies:** US-001

**Acceptance Criteria:**

1. **Given** a project, **when** I save a role with a name and responsibilities, **then** it appears in that project's role list and is available for assignment.
2. **Given** missing required role information, **when** I save, **then** the app identifies the missing information and retains my input.
3. **Given** an assigned role, **when** I edit its responsibilities, **then** the role details update without losing existing task assignments.
4. **Given** a role definition, **when** I view it, **then** its existence does not imply an agent has been launched or is running.

**Open questions:** Should roles be reusable across projects? Proposed MVP keeps definitions within each project.

### US-004 — Create and prioritize tasks

**Story:** As a solo builder, I want to record tasks and their priority so that I can organize what needs to happen next.

**Priority:** Must

**Links:** Task coordination

**Dependencies:** US-001

**Acceptance Criteria:**

1. **Given** a selected project, **when** I save a task with a title, optional description, and priority, **then** it appears in that project with its saved details and initial status.
2. **Given** a blank title, **when** I save, **then** the app rejects the task with an explanation and retains my input.
3. **Given** an existing task, **when** I edit its title, description, or priority, **then** its assignment, status, and linked documents are preserved.
4. **Given** tasks with different priorities, **when** I order the task list by priority, **then** the highest-priority tasks appear first.

**Open questions:** None blocking. Assumption: priorities are High, Normal, and Low; Normal is the default, and initial status is Planned.

### US-005 — Assign task responsibility

**Story:** As a solo builder, I want to assign a task to an agent role or myself so that ownership is explicit.

**Priority:** Must

**Links:** Agent role management; Task coordination

**Dependencies:** US-003, US-004

**Acceptance Criteria:**

1. **Given** a task and a role in the same project, **when** I assign the role, **then** the task shows that role as its owner.
2. **Given** a task, **when** I take ownership myself or reassign it, **then** the current owner is updated without discarding the task's work or documents.
3. **Given** a task with no owner, **when** I view it, **then** it is explicitly labeled Unassigned.
4. **Given** a role belonging only to another project, **when** I choose an owner, **then** it cannot be assigned to the current task.
5. **Given** a role assignment, **when** it is saved, **then** it is treated as responsibility and does not claim agent execution has started.

**Open questions:** None blocking. Assumption: one current owner per task; unassigned tasks are allowed.

### US-006 — Track task progress and blockers

**Story:** As a solo builder, I want to update task status and record blockers so that I can coordinate work and identify what needs intervention.

**Priority:** Must

**Links:** Task coordination; Progress tracking

**Dependencies:** US-004

**Acceptance Criteria:**

1. **Given** a task, **when** I select Planned, In Progress, Blocked, or Done and save, **then** the task displays that status and its last update time.
2. **Given** a task being marked Blocked, **when** I save without a blocker explanation, **then** the app requests an explanation before applying the change.
3. **Given** a blocked task, **when** I resolve the blocker and change its status, **then** it no longer appears as currently blocked.
4. **Given** a completed task requiring more work, **when** I return it to In Progress, **then** it reappears among active work.
5. **Given** a failed status save, **when** the update fails, **then** the app retains the last saved status and clearly shows the failure with a retry option.

**Open questions:** None blocking. Assumption: the builder updates status manually; these states do not represent verified execution telemetry.

### US-007 — Maintain project documents

**Story:** As a solo builder, I want to create, read, and revise product documents within a project so that I can retain its decisions and context.

**Priority:** Must

**Links:** Document management

**Dependencies:** US-001

**Acceptance Criteria:**

1. **Given** a project, **when** I save a document with a title and content, **then** it is listed in that project and can be reopened with the saved content.
2. **Given** a saved document, **when** I revise it, **then** the current content updates and its update time is visible.
3. **Given** a missing title or empty content, **when** I save, **then** the app identifies the problem and retains my input.
4. **Given** a failed save, **when** I attempt to leave the editor, **then** the app indicates that changes are unsaved and lets me stay to recover them.
5. **Given** a project with no documents, **when** I open its documents, **then** an empty state offers creation.

**Open questions:** Are file uploads, external links, or revision browsing required for the first release? Proposed MVP provides editable documents; these additions remain undecided.

### US-008 — Connect documents and task outputs

**Story:** As a solo builder, I want to link documents to relevant tasks so that I can find the supporting context and resulting work together.

**Priority:** Must

**Links:** Document management; Task coordination

**Dependencies:** US-004, US-007

**Acceptance Criteria:**

1. **Given** a task and a document in the same project, **when** I link the document as supporting context or an output, **then** the task shows the document and its relationship.
2. **Given** a linked document, **when** I open it from a task, **then** the correct document opens and I can return to the task.
3. **Given** a document already linked with the same relationship, **when** I try linking it again, **then** no duplicate association is created.
4. **Given** a document belonging only to another project, **when** I choose documents to link, **then** it is not offered as a link target.
5. **Given** an existing association, **when** I remove the link, **then** the document itself remains available in the project.

**Open questions:** None blocking. Assumption: links open the current saved document; pinning a specific revision is deferred.

### US-009 — Review project progress

**Story:** As a solo builder, I want an overview of project progress and blockers so that I can choose what needs attention next.

**Priority:** Must

**Links:** Progress tracking

**Dependencies:** US-004, US-006

**Acceptance Criteria:**

1. **Given** tasks in multiple states, **when** I view project progress, **then** counts for Planned, In Progress, Blocked, and Done match the saved tasks in that project.
2. **Given** a status count, **when** I select it, **then** I can inspect the tasks contributing to it.
3. **Given** blocked tasks, **when** I inspect project blockers, **then** each shows its explanation and owner, including Unassigned where applicable.
4. **Given** a task status change saved successfully, **when** I return to the overview, **then** the totals reflect the saved change.
5. **Given** no tasks, **when** I open progress, **then** the app shows an empty state rather than implying the project is complete.
6. **Given** unavailable project data, **when** the overview cannot load, **then** it shows an error and retry action rather than reporting zero work as fact.

**Open questions:** None blocking. Assumption: task counts are sufficient for MVP; no estimate of overall product completion is implied.

### US-010 — Review a task's changes

**Story:** As a solo builder, I want to inspect task ownership and status changes so that I can reconstruct how work progressed.

**Priority:** Should

**Links:** Progress tracking; Task coordination

**Dependencies:** US-005, US-006

**Acceptance Criteria:**

1. **Given** a saved ownership or status change, **when** I inspect task activity, **then** I see the previous value, new value, and time of the change.
2. **Given** several changes, **when** I inspect activity, **then** their order is clear and reopening the task preserves the recorded entries.
3. **Given** an update that failed to save, **when** I inspect activity, **then** no successful change is recorded for that failed attempt.
4. **Given** a new task without changes, **when** I inspect activity, **then** an empty state explains that no changes have been recorded.

**Open questions:** None blocking. Assumption: this history covers changes made through AgentBoard, not external agent events.

## Coverage & Scope Notes

- Product project management: US-001 and US-002.
- Agent role management: US-003 and US-005.
- Task coordination: US-004, US-005, US-006, and US-008.
- Document management: US-007 and US-008.
- Progress tracking: US-006, US-009, and US-010.

**Proposed MVP boundary:** One builder coordinates projects, role definitions, manually updated tasks, and editable project documents. These behaviors refine the draft Vision and remain subject to product-owner review. No generated story or validation result constitutes approval.

**Deferred scope:** Executing agents, live telemetry, cross-project reusable roles, external integrations, document uploads, revision pinning, collaboration permissions, and billing. Deferment is a planning assumption, not a permanent exclusion. The product's platform and hosting remain undecided; local storage for these planning artifacts does not decide the app's deployment model.

**Decisions for the product owner:** Confirm whether the first release must launch and control agents; confirm the first platform and data-storage expectations; confirm document input types and the proposed manual-status workflow. Architecture should explicitly resolve these choices before committing to integrations or deployment.

**Permission coverage:** Same-project assignment and document linking are covered in US-005 and US-008. Multi-user authorization is outside this proposed single-builder scope and must be specified if shared access is added.

**Traceability:** The current Vision uses feature names rather than goal/use-case IDs. Links above refer to those names without inventing missing IDs. Each story ID remains stable across future revisions.
