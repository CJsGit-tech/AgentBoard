# Product Vision — AgentBoard

> Owner: Product Manager | Version: 0.1.0 | Status: draft | Last Updated: 2026-11-17
> Summary: AgentBoard helps solo builders manage AI agents and product projects by coordinating roles, tasks, documents, and progress in one place.

## 1. Product Overview

AgentBoard gives a solo builder a shared workspace for each product project: what the project aims to deliver, which agent roles are responsible, what work is underway, and which documents record the decisions and results. The builder stays responsible for priorities, scope, and acceptance of outputs.

**Confirmed direction:** The product is an app for solo builders managing AI agents and product projects together. Its core concerns are roles, tasks, documents, and progress tracking. These requirements come from the product owner's brief in this conversation.

**Proposed direction — assumption:** Begin with coordination and visibility. Whether AgentBoard also launches and controls agents is an open product decision; a configured role must not imply a running agent.

## 2. Problem & Opportunity

A solo builder needs to coordinate several kinds of work without a dedicated project manager. Agent responsibilities, task updates, and product documents need enough shared context to support decisions and handoffs.

**Problem hypothesis:** When this information is scattered across conversations and tools, the builder spends time reconstructing context, misses blockers, and cannot easily connect an agent's output to the work it was meant to complete. This has not been validated through user research.

The opportunity is to make project state inspectable in one place, so the builder can decide what to do next and assess completed work with its supporting evidence.

## 3. Target Users

**Primary user:** A solo builder developing a product with help from multiple AI agent roles. The same person sets priorities, coordinates work, and reviews results.

**Assumption:** The first version serves one builder managing several projects, rather than teams with complex permissions. Platform, hosting, and device requirements remain undecided. Core actions should support keyboard use, readable text, and status indicators that do not rely on color alone.

## 4. Value Proposition

AgentBoard connects project intent, agent responsibilities, work items, and documents. A builder can see who owns a task, what it needs, what it produced, and what is blocking progress without reconstructing that relationship from separate conversations.

This is the intended value proposition, not a validated claim of differentiation or time savings.

## 5. Goals & Success Criteria

All numeric targets below are proposed pilot targets, not measured results or approved commitments.

| Goal ID | Desired outcome | Success signal / target | Evidence or assumption |
| --- | --- | --- | --- |
| G-001 | Understand a project's current state quickly | In a pilot, 4 of 5 builders identify current work, a blocker, and the next action within 60 seconds | Progress tracking is confirmed; target is an assumption |
| G-002 | Make responsibility clear | Every active task has an explicit owner, including the builder where appropriate | Role and task coordination are confirmed; completeness rule is proposed |
| G-003 | Preserve context across work and outputs | In a pilot, 4 of 5 builders locate a task's supporting document and outcome without searching another tool | Document coordination is confirmed; scenario and target are assumptions |
| G-004 | Keep progress trustworthy | Every displayed task status has a visible source or update time; unverified execution is not presented as confirmed | Proposed trust requirement |

## 6. Core Use Cases

| ID | User | Situation and task | Expected value |
| --- | --- | --- | --- |
| UC-001 | Solo builder | Create or reopen a product project and record its purpose and scope | Establish shared project context; supports G-001 |
| UC-002 | Solo builder | Define agent roles and responsibilities within the project | Clarify ownership before assigning work; supports G-002 |
| UC-003 | Solo builder | Create, prioritize, assign, and update tasks, including blockers | Coordinate the next action; supports G-001 and G-002 |
| UC-004 | Solo builder | Associate product documents and task outputs with the relevant project and work | Preserve decision and handoff context; supports G-003 |
| UC-005 | Solo builder | Review progress, blocked work, and outputs awaiting review | Decide what to unblock, revise, or accept; supports G-001 and G-004 |

## 7. MVP Scope

The following boundaries are proposed assumptions for review, derived from the confirmed product direction.

**In scope:**

- A project list and project context with purpose and scope (UC-001).
- Editable agent role definitions and task ownership (UC-002, UC-003).
- Task priorities and explicit states such as planned, in progress, blocked, awaiting review, and done (UC-003, UC-005).
- Project documents or references linked to relevant tasks, with identifiable current versions (UC-004).
- A project overview showing active work, blockers, review items, and next actions, with status freshness visible (UC-005).
- Builder review of outputs before marking work accepted (UC-005).

**Out of scope for this proposed MVP:** Team administration, agent marketplaces, billing, and unattended autonomous orchestration. Running agents and importing their live state are deferred decisions, not promised capabilities. The local storage selected for these planning documents does not determine the app's eventual storage or deployment model.

## 8. Assumptions & Risks

| Type | Assumption / risk | How it can be validated or mitigated |
| --- | --- | --- |
| Assumption | Solo builders find a shared coordination workspace more useful than their current process | Observe representative builders completing UC-001 through UC-005 and compare context-finding effort |
| Risk | Manual updates become stale and undermine progress tracking | Test update effort; show update times and distinguish manual status from verified execution |
| Risk | Managing role definitions is mistaken for controlling live agents | Use explicit role, assignment, and execution states; promise live controls only after integration scope is agreed |
| Risk | Documents and tasks disagree about current decisions | Link the relevant document version to work and flag revisions for review |
| Risk | Project documents contain sensitive product information | Decide storage, access, export, and deletion expectations before selecting the architecture |

## 9. Open Decisions

Owner for each decision: Product owner, supported by the Product Manager.

1. Does the first release coordinate agent work only, or also launch, stop, and observe real agent runs? Which agent environment must it support first?
2. What platform should ship first, and should product data stay on the builder's device or be hosted?
3. Which existing task or document tools must the first release work with, if any?
4. Are the proposed MVP exclusions and pilot success targets appropriate for the first release?

These decisions remain open. This document is a working draft; it does not authorize implementation or imply product approval.
