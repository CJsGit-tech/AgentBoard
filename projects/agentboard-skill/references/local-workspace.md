# Local workspace — opt-in fallback and canonical file rules

AgentBoard is the default canonical workspace when installed. File-only projects are for users who choose not to install/use AgentBoard, or explicitly choose file-only mode. They never queue writes for later upload.

**Terminology:** AgentBoard can run locally on the personal computer and still be the connected app workspace. “Local-only files” means the separate Markdown/manifest fallback with no AgentBoard records.

## Mandatory confirmation before fallback

A named project and writable workspace **are not enough** to authorize storage changes. If AgentBoard is not installed and no target has been chosen, propose file-only mode and wait for the user's choice before creating files. If an installed app fails to start or lacks a needed capability, report the blocker and stop; do not propose file-only mode as an automatic recovery path. Do not confuse a command to set up an AgentBoard project with permission to redirect that setup to disk.

Exact recommended question:

> AgentBoard is not installed. Choose a storage target for **<ProjectName>**: **Use file-only mode** at **<resolved-path>**, or **Cancel** and install/connect AgentBoard first. File-only records will not be part of an AgentBoard workspace.

Before the user chooses file-only mode, perform read-only availability checks, inspect existing metadata and calculate the proposed path. Do not create `projects/`, `agents/`, `docs/`, temporary draft files, or manifests. Do not run the scaffold or artifact-saving tools. Cancel leaves both app records and files unchanged.

Consent is **scoped to the named project** and recorded in `project-manifest.json` as `project.local_storage_confirmed: true` and `project.local_storage_confirmed_at`. An explicit request to use local storage, e.g. `AgentBuild Setup "Project" --local`, constitutes approval. A prior manifest with this confirmation permits subsequent document commands without re-prompting. An old local project **without** recorded confirmation must request approval before being modified. Do not assume existing files imply consent to migrate their status.

## Path and setup, only after consent

Use the existing approved local project path where available. Otherwise default to `<cwd>/projects/<slug>` in the current workspace; apply `--root` only for an established project root. Do not put projects inside the installed skill. Use the scaffold's slug logic, not an improvised name-to-path conversion.

```sh
python3 <skill-root>/scripts/scaffold_project.py \
  --name "<ProjectName>" --user-approved-local
```

`--user-approved-local` is a **required explicit assertion of user approval** for first-time local writes, never a flag agents may set as a shortcut. Running the script without the flag does not create/update an unconfirmed local project. Existing projects with recorded approval can be reused without the flag.

The project contains:

```text
projects/<slug>/
  project-manifest.json          # local consent, documents, status and versions
  agents/                       # six editable role charters, not running agents
  docs/                         # real documents generated by subsequent commands
  history/                      # created on first document revision
```

Setup is idempotent and leaves existing customized role files and documents unchanged. No blank product documents are created. Set `project.storage_mode = "local"`, `project.sync_state = "local_only"`. Do not use `pending_sync` absent an explicit later sync request.

## For each document command

1. Read the existing local manifest and role charter if previously approved. If no project exists, **ask the same storage question first**; do not auto-scaffold.
2. If an existing local manifest has no `local_storage_confirmed: true`, **ask** before writing anything; after approval, call scaffold with `--user-approved-local` to update consent non-destructively.
3. Read the applicable folder README first, then only relevant story/topic files, plus actual Vision and other prerequisites; never fabricate prerequisite documents or silently expand MVP scope.
4. Author a **complete project-specific document** with real metadata, human decisions and explicitly labeled assumptions (not an unfilled template).
5. For folder-layout stories/architecture, edit individual Markdown files, maintain README links, preserve history, and update manifest metadata following `references/document-folders.md`. Do not pass folder artifact entries to the single-file saver. For single-file artifacts, save through `scripts/save_artifact.py --project "<project-path>" --artifact vision --source "<authored-file>"` (other keys: `stories`, `architecture`, `architecture-svg`, `design`, `tokens`, `review`). The save utility checks project consent. For changed existing files, use `--revise` to archive the old version; never silently overwrite approved documents.
6. Validate with `scripts/validate_project.py` and perform a separate semantic review. Report actual paths, versions, status and unresolved decisions.

## Local/remote boundary

- Local mode is a valid working mode **after the user chooses it**. Do not label it a remote error or an implicit sync queue.
- If a new remote integration becomes available, keep local canonical until the user explicitly changes the storage target and authorizes any sync/reconciliation.
- No guessed AgentBoard IDs, unsupported API calls, or automatic remote uploads.
- Help and Status are read-only; they can answer without triggering project creation or consent prompts for writing.
