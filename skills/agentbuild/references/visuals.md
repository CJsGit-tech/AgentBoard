# Create Visuals

Use this contract when preparing Design Profile within Create Documents or running Create Visuals. UserScreens supplies Feel/Flow/Show intent; Design Profile realizes that intent as concrete local screen designs. Apply the [change review rules](reviews.md) to new screens and feature changes, keeping impact findings with the local/chat proposal during preparation. Publication and implementation wait for their required checks. Upload the reviewed package the user approves without requesting that approval again.

For an explicit chat-only request, discuss and write the design specification in chat; defer workspace preparation and file-based builds until requested. Report only the preparation actually completed.

## Build the local draft

1. Resolve the project, its local root and [workspace folders](local-workspace.md), and relevant User Experiences, UserScreens, and Design Profile content from saved records or current local/chat drafts. Prepare missing directories under the current command authorization. Read saved sources and revisions, and retain the identity/content of unpublished sources in local metadata. Missing source records or a missing destination Design Profile do not require an upload before drafting. Use the confirmed design direction; follow the [direction review](planning.md#choose-a-visual-direction) when choosing a new one. Use the relevant [document question subset](planning.md#document-questions) and conversational follow-ups for missing design context.
2. Check the project's routes and controls against its screen inventory. For a project canvas, show current screens and their important views first, then clearly group planned screens. For a scoped request, cover the named journey and states. Use local sample records for demos and identify illustrative data.
3. Before building screen drafts, write and present the [Figma-style design narrative](#figma-style-design-narrative) for the selected screens. Save it as `design-narrative.md` beside the gallery. Continue into drafting under the existing authorization unless the user requested a review checkpoint or a missing decision blocks the design.
4. Build the drafts with [React and Mantine](#mantine-drafts), then bundle an interactive HTML canvas in the resolved local flow/version folder. Reuse existing conventions and preserve published version folders as described in [Local workspace](local-workspace.md#use-the-workspace). Use the built `gallery.html` as its entry. Include a readable opening view, a left sidebar index with click-to-switch previews, pan, zoom, and Fit all. Follow the [local gallery layout](#local-gallery-layout). Provide readable HTML narrative notes linked to their screens, separate from the simulated application UI. Keep scripts, fonts, subframes and other required assets local, with relative paths. Design the gallery to run in an iframe with scripts and local UI interactions, isolated from AgentBoard data and external services.
5. Save `canvas-files.json` beside the entry. It lists each file needed to run the reviewed canvas once, relative to the manifest. For a self-contained gallery use `["gallery.html"]`. Include nested screen pages and built runtime assets, including the bundled React and Mantine code and CSS. Keep raw `node_modules`, build sources, `design-narrative.md`, keys, workspace exports and unrelated files out of the publication. The server accepts HTML, JS, CSS, WOFF2, SVG, PNG, JPEG and WebP, up to 200 files and 12 MiB in total.
6. Retain saved source revisions and unpublished source paths/content digests in the [local draft baselines](local-workspace.md#location-map-and-draft-baselines). Chat-only sources need their exact reviewed content and conversation reference. Prepare `publication.json` at upload time after the approved source documents have been saved and read back; do not invent IDs or upload drafts just to populate it.
7. Build and type-check the React draft. Open the built local gallery and check every frame against its narrative and UserScreens Feel/Flow/Show intent: hierarchy, widget appearance, button locations, information density, progressive disclosure, screen order, labels, readable zoom, overview, the narrow layout and representative interactions. Check the complete visible interface and confirm required assets load without external network access. Give the user the local gallery, narrative, and proposed document content. Apply requested revisions locally. Present the exact design package for approval before storage writes; an explicit request to upload an already reviewed package is sufficient.

## Local gallery layout

Use the PocketReminder local draft's review format as the default gallery shell; adapt its styling to the project's Design Profile rather than copying its product content.

- **Left sidebar index.** Place the screen index beside the preview, not in a horizontal strip or a grid above it. Clicking an entry switches the main preview in place. Highlight the selected entry with a soft surface and an accent; expose its selected state to assistive technology. Use readable screen names and distinguish current screens from proposed experiences. Order current screens first, then planned screens; group form drafts clearly.
- **Independent scrolling.** Give the sidebar its own vertical scroll when the inventory exceeds the viewport. Keep it available while reviewing the preview, with a visible scrolling affordance. Every entry must be reachable; do not hide additional screens behind horizontal scrolling. On narrow windows, use a collapsible index with a visible toggle and the selected screen name; selecting an entry closes it and restores preview space.
- **Preview stage.** Center one selected screen in a soft, spacious stage. Use a device frame for mobile designs and the appropriate application frame for other products. Keep gallery navigation, screen purpose, narrative, zoom and Fit all outside the simulated app. Fit the opening preview to the available space without clipping its primary controls; allow the simulated screen's content to scroll.
- **Complete form inventory.** For a whole-app review, inspect current source routes, template/type catalogs and editors. Provide a directly selectable form draft for every supported item/event type, alongside its list and detail views. Follow the actual editor's shared fields and type-specific defaults; do not turn deprecated fields into new required fields. Label saved-data-only types as edit drafts instead of implying they are available for creation. For a scoped review, cover the requested types and states and state the coverage explicitly.
- **Reviewable interactions.** Use illustrative records and working local controls for the reviewed flow. Label simulated save feedback accurately. Keep current implementation and proposed behavior distinguishable; the gallery does not write application data or sync with external services.
- **Layout verification.** Check the sidebar with the complete inventory, including the last entry; click entries near both ends and confirm the selected preview changes. Check desktop and narrow layouts, independent scrolling, readable sizing and absence of horizontal page overflow. Capture evidence of the sidebar and selected preview together.

## Figma-style design narrative

Write a concrete design specification for each screen before implementing its UI. Use the screen's name and its source journey or UserScreens reference, followed by:

- **User moment and screen purpose.** Explain what brought the person here, what they need to understand, and the next decision or action.
- **Composition and hierarchy.** Describe the visible regions in reading order, navigation, grouping, alignment, density, and what receives emphasis. State the requested grid or proportions and how the layout adapts to narrower screens.
- **Visual appearance.** Specify surface colors, typography roles and sizes, spacing, borders, corner shapes, elevation and icon treatment using the confirmed design tokens. Use concrete choices instead of adjectives such as "clean" or "modern" alone.
- **Widget specifications.** Describe each important widget's anatomy, shape, content order, metric meanings and visual treatment. Cover hover, focus, selected and disabled treatments where relevant. Explain which question each chart answers; pair progress graphics with readable values.
- **Buttons and controls.** Name each action, its exact location relative to the content, primary or supporting emphasis, label, size, and enabled conditions. Describe the feedback or destination after activation.
- **Flow and states.** Show entry, selection and destination, when navigation or details become available, and relevant empty, loading, error and recovery states. Keep proposed behavior consistent with User Experiences; mark unresolved choices Open.
- **Principles and rationale.** Connect each important choice to a named design principle and the user need it serves. For example: "Hierarchy: project names lead each folder so returning users can recognize their workspace" or "Progressive disclosure: reveal project navigation after selection so actions have a project context." Explain the visible application of the principle rather than listing principle names alone.

Keep shared visual rules in one place and reference them from each screen. Update the narrative when the design changes so the gallery remains a reviewable explanation of the rendered result.

## Mantine drafts

Use React and real Mantine components for HTML screen drafts unless the user explicitly requests another tool or medium. Reuse the project's installed compatible React and Mantine versions, helpers and components when available. Keep a draft in an isolated preview entry rather than changing production routes. Follow the host's dependency rules if packages need to be added.

Use `MantineProvider` and the required Mantine styles. Apply the Design Profile's palette, typography, spacing and control shapes through the theme and component styles. Reuse Mantine controls, layout primitives, dialogs and progress components instead of rebuilding their behavior. Compose custom visual forms, such as folder-shaped project cards, from those primitives when the narrative calls for them; do not let a default component template replace the agreed composition.

Deliver built HTML with local JavaScript, CSS, fonts and assets. Use relative asset paths and bundle React and Mantine into the runtime output; a canvas must not depend on a development server, remote CDN or browser package imports. Include only the runtime files in `canvas-files.json`. Keep the gallery's pan and zoom controls outside the simulated application UI. If Mantine or its build cannot run, report the blocker rather than presenting a static imitation as a Mantine draft.

## Publish and verify

1. Verify approval for the exact reviewed package, then use the verified AgentBoard launcher and document schema. Recheck local draft baselines and current saved records. Save only the approved source document drafts needed for the publication, including the Design Profile when missing or changed, using the [document save rules](planning.md#planning-documents). Resolve ambiguous matches and reuse intended IDs. Read records back and complete their impact reviews. UserScreens and other source drafts need their own approval or inclusion in the approved package; canvas approval does not authorize unseen document changes. If saving fails, keep the remaining work local and report the partial result. Verify the destination Design Profile (`design-topic`), URL, and current revision; uploading the attachment preserves its approved text.
2. Prepare `publication.json` beside the reviewed manifest with a `change_note` and the exact saved source revisions whose content the draft represents, for example `{"change_note":"Added the recovery screen","sources":[{"document_id":"<verified-source-id>","revision":3}]}`. Compare saved content with the reviewed local sources before recording their IDs/revisions. Run the helper with this metadata. It sends only listed runtime files to `publish_canvas`, then reads back files and metadata. Use Claude for Claude Code. The positional ID/revision refer to the destination Design Profile; `sources` identifies the saved document versions represented by the design. If source content changes, refresh the draft and review before upload.

   ```sh
   python3 <skill-dir>/scripts/publish_canvas.py <absolute-agentboard-launcher> Codex <document-id> <revision> <canvas-files.json> <verified-profile-url> --publication <publication.json>
   ```

3. A changed bundle or changed publication metadata creates a numbered version. Repeating the latest identical files, note and source references preserves its version. The server snapshots the source names and validates that the referenced revisions are current and belong to the same project. On a destination revision conflict or uncertain write, read the latest profile before retrying and compare its saved files and metadata with the reviewed draft. If the latest publication already matches, report that version. A changed source revision requires reading the changed document and checking the draft against it. Update the draft and its source references together, then continue the local review flow for any design changes. Editing a source document alone leaves existing publications fixed.
4. Read back the profile and verify the saved file digest, change note and source revisions. Find the published version in Canvas; the current UI uses searchable cards. Open its full viewer and verify the reviewed screens, publication note, source names, revisions, publisher, and time in version history. Design Profile's Open canvas link opens the same viewer. Keep this publication verification procedure here; other skill files link to it. Return the profile link and version, and link the full viewer when its route is verified. The Canvas list is `/#canvas`, and a publication opens at `/#canvas/<profile-id>/<version>` on the verified app origin. If only the local draft succeeded, link it and name the remaining step. When a ticket link was requested, revision-check the ticket and append the canvas to Context, preserving existing links.

For an explicit still-image request, keep the PNG workflow available. Save the PNGs locally and, after upload approval, attach them to a project screen inventory with `attach_visual` or `scripts/attach_visual.py`. See [Records](records.md).
